# session 模块

## 职责
agent 运行时核心。驱动「接收输入 → 调 LLM → 执行工具 → 持久化」的主循环，并实现两段式 delivery（steer/queue）、上下文压缩、会话恢复、title 生成、可中断（turn 边界 + mid-tool 硬中止）。

## 边界与非目标
- 不做 HTTP / 终端 IO（由 web/cli/tui 负责）。
- 不直接连数据库驱动——经 `Store` trait 抽象。
- 非目标：MCP / 权限确认（当前未实现）。
- skills 仅承接「可选的系统提示注入」：`SessionState.skill_prompt`（`Arc<Mutex<Option<String>>>`）是共享可变状态——TUI 持有 `Arc` 克隆并直接写入（绕过 cmd channel），`run_one_llm_call` 每 turn 经 `skill_prompt_cloned()` 读取最新值。每轮 `build_system` 把它作为 `## Active skill` 段追加到系统提示末尾（最高优先级）。skill 的发现/解析/选择 UI 不在本模块（见 core 的 `skill` 模块与 tui 的 `menu` 模块）。

## 关键抽象
- `SessionState`（`src/lib.rs`）：`id/messages/agent/model/config/client(Arc<dyn ChatStream>)/store(Option<Arc<dyn Store>>)/cancel(Option<CancellationToken>)/skill_prompt(Arc<Mutex<Option<String>>>)` + `working_dir/last_usage/persisted_count/session_created`。`cancel` 由调用方挂载（`with_cancel`）：web 经 `POST /interrupt`、tui 经双击 Esc 触发；同一 token 在 run_loop 顶部与 mid-tool select! 两处生效。`skill_prompt` 是共享可变状态：TUI 经 `Arc` 克隆直接写入（`set_skill`/`with_skill`），`run_one_llm_call` 每 turn 经 `skill_prompt_cloned()` 读取最新值，由 `build_system` 注入系统提示。此设计修复了 session 运行中激活 skill 不生效的 bug（旧设计经 cmd channel 发送 `SetSkill`，worker 阻塞在 `run_loop` 内无法及时处理）。
- `record(&mut self, msg)`（`src/lib.rs`）：push 到内存 + 若有 store 则持久化（best-effort，失败仅 warn）。runner 所有 message 入口都走它。
- `SessionEvent`（`runner/event.rs`，16 变体）：SSE/持久化的**单一真相源**三方法——`sse_kind()`（细粒度事件名字符串，如 `text_delta`/`reasoning_delta`/`subagent_child`/`plan_handoff`）、`sse_data()`（与 SSE 线格式一致的 JSON payload）、`coarse_kind()`（12 变体 `EventKind`，仅作 DB `type` 列与回退）。web（`SseEvt::from_session_event`/drain 持久化）与 TUI（`worker::persist_event`）都走这三方法，使 live 广播与 replay 的 kind/payload 完全一致；store 的 `sse_kind` 列保住 replay 细粒度（旧记录 `None` 时回退 coarse）。
- **事件缓冲 flusher**（`src/event_sink.rs`，导出 `EventSink`/`spawn_event_flusher`/`run_flusher`）：把 O(tokens) 的 token delta 落库降到 O(turn)。UI/SSE 实时投递路径（`on_event`）完全不动——每事件仍实时转发；只有磁盘路径走批量。`EventSink` 是可 clone 的 unbounded-channel push 句柄；`run_flusher` 只缓冲 `TextDelta`/`ReasoningDelta`（均 coarse-map `EventKind::TextDelta`），其余类型立即 flush；阈值 `DELTA_BATCH=512`/`DELTA_BYTES=8KiB`。无损契约：丢弃所有 sink clone + `await` flusher 句柄即保证剩余缓冲全落库（turn 边界/channel close 触发最终 flush）。崩溃最坏丢失当前 turn 少量未 flush delta，权威文本仍经 per-turn `messages` append 落地。调用方（TUI `worker`/web `handle`/headless）在 `on_event` 闭包内 `sink.push(&ev)`，run 结束后 `drop(sink)`+`flusher.await`。subagent（`runner/subagent.rs`）与 replay（`resume.rs`）子事件路径直接用 `run_flusher`+unbounded channel。
- `run_loop`（`runner/mod.rs`）：drain 主循环。每轮顶部：① cancel 检查（turn 边界，web/tui 触发）② **claim_steers**（提升 pending steer，safe provider-turn boundary）③ 压缩判定 ④ 单次 LLM 调用 ⑤ 工具执行（**一批 tool_calls 并发**：`FuturesUnordered`，每个 future 开头 `yield_now().await` 保证全部被调度（否则快速响应退化为串行），`ToolStart` 按调用顺序预声明、`ToolEnd` 按完成顺序 emit，结果按原始 index 重排保证 Tool message 确定性；事件经共享 `Sink`——`Arc<Mutex<&mut (dyn FnMut+Send)>>` + `emit`——多发并发安全）⑥ 若无工具调用（idle）→ **claim_one_queued**（恰好一条，返回 `(seq,input)` 并 emit `QueueConsumed{seq, text}`（`text` 为 prompt 原文，供前端激活瞬间回显） 让前端即时收缩 pending 镜像）：控制命令（/act、/plan、/act_clear_context）直接应用不耗 LLM turn、可连排；真实 prompt 记录一条后于下一 idle 边界发 `Done`——**每 run 至多一条 queued 真实 prompt**，剩余行保持 pending 待下次显式提交（steer 才是清空路径：`claim_steers` 在每轮 turn 边界提升全部 pending steer）。硬中止：`run_one_llm_call` 的流接收循环与 `execute_call` 的工具 `.await` 均包在 `tokio::select!` 中监听 `await_cancel(session)`；触发后前者回空 turn、后者回 `interrupted` 工具结果；工具批在 cancel 下仍 **drain 至完成**（不 break——否则丢弃在飞 subagent future 会漏发 `SubagentEnd`/`complete_subagent_task` 并留下无 result 的 tool_use），run 在下一轮顶部 cancel 检查收尾。bash 工具设 `kill_on_drop(true)`，select! 取消即丢弃 future → 杀子进程。**bash 进程经 `pre_exec(setsid)` 自成新会话/进程组（load-bearing：否则子进程仍共享控制终端、能直写 `/dev/tty`——sudo 提示/进度条/后台子进程的输出绕过 pipe、落到 alt 屏光标处即 TUI composer/input 区，正是『输出跑到输入区』bug 的根因；新会话令 `/dev/tty` 不可用、强制所有输出走被分捕的 pipe）**。**bash 前台运行并有 130s 超时**（`BASH_TIMEOUT_SECS`；`cfg(test)` 下为 1s 便于测试）：工具 future 拥有 `Child`，用 `tokio::time::timeout(BASH_TIMEOUT_SECS, child.wait())` 与自然退出赛跑；超时**不杀进程**——经 `bg::handoff()` 交接给后台 supervisor 继续运行，工具返回**非错误**结果（`is_error: false`，命令仍在跑），含 `BASH_TIMEOUT_MARKER`（`"[bash-timeout:"`）、pid 与输出文件路径（`/tmp/opencoder_bg_{pid}.output`）；非 Unix 平台回退 `child.kill()`。bash 仍豁免 runner 的 600s 叶级工具安全网（`execute.rs::DEFAULT_TOOL_TIMEOUT`，自带更短超时）。runner 层**连续 bash-timeout 去重**：`dedup_consecutive_bash_timeouts()` 在连续 bash 超时结果中仅保留**第一条**完整内容，后续替换为第一条（同 pid/同输出文件，模型读同一文件）；非超时 bash 结果重置 streak，非 bash 工具**不**重置；状态 `bash_timeout_first` 跨 turn 持久化。spawn 后立即 `bg::register(pid, pgid, session_id)` 使 `/ps` 能列出、`/stop` 能强杀**正在运行**的命令；`wait()` 返回时 `bg::unregister(pid)`（幂等——若 `/stop` 已先 `kill_all()` 移除条目则为 no-op）。前台阶段仍用共享 `Arc<Mutex<BgState>>` 增量缓冲 stdout/stderr（drain task 缓冲避免管道写满阻塞 `wait()`），无 file 模式。自然完成时先 `kill(-pgid, SIGKILL)` 强制 EOF（清继承管道写端的孙进程——否则 `cmd &` 留孙进程持管致 drain 永久 hang，而 bash 豁免 runner 安全网无兜底），drain 限 2s 有界等待（与 `bg::handoff` 同上限）。`setsid` 仍使 pid==pgid（load-bearing：隔离 `/dev/tty`，且 `kill(-pgid)` 一击尽杀整棵后代树）；`kill_on_drop(true)` 仅杀直接 bash 子，作 select! cancel / future drop 的硬中止回退。全局注册表 `OnceLock<Mutex<HashMap<pid,BgEntry>>>`；TUI `/stop` 调 `bg::kill_all()` 强杀全部已注册组，headless `run.rs` 第二次 Ctrl-C 强退时 `bg::cleanup_all()`（=kill_all + 删 temp 文件）。子 agent 复用父 token（`child.cancel = parent.cancel.clone()`）。doom-loop 守卫：`DOOM_THRESHOLD=3`，连续空 turn 达阈值后注入提示打破循环。**tool-failure 守卫**（`src/tool_guard.rs` + `core::ToolGuardConfig`，默认 `max_consecutive_failures=5`）：run_loop 维护每轮 `FailureMap`（按工具名），工具结果批后调 `tool_guard::record` 记录——成功清零、失败递增；达阈值即发 `SessionEvent::Error` 并 `break` 中止当前 turn，失败间施加指数退避（`backoff_base_ms*2^(n-1)`，封顶 `backoff_max_ms`）。与 doom 守卫互补：doom 按 `name:input` 签名，本守卫按工具名，故模型微调入参仍能被拦。设阈值为 0 禁用。**plan 模式 bash 写拦截**：`execute_call` 在 plan agent 调 bash 前调用 `bash_guard::classify`，若为写命令（文件重定向 `> file`/`>> log`/`&> out`、`tee <真实文件>`、变异/git写/包管理/就地编辑）则返回描述性错误给模型（"Blocked in plan mode"），不执行。判只读：fd-merge（`2>&1`/`1>&2`）与重定向到 `/dev/null`（含 `tee /dev/null`、裸 `tee`）——bash 工具已分捕 stdout/stderr 故无副作用；此判定在子 shell/花括号组内同样生效（`read_redirect_target` 在 `)`/`}`/`]`/`#` 处干净终止，不再误吞元字符）。plan agent 无 plan_exit 工具——计划以纯文本输出、turn 自然结束；用户 Shift+Tab 切 act 后 TUI 发 `SwitchAndStart` → worker 切 agent 后**先 `plan_handoff::handoff` 清空 transcript**（提取最后一条非空 assistant 文本作为「最终计划」，重置 `session.messages` 为单条合成 user 指令、发 `TranscriptReset` 让 UI `replay_into_chat` 重建为只含计划），再空 prompt 进 `run_loop`（系统提示变 act，act 以只含计划的干净 ctx 开始执行）。store 不动——append-only 保留完整原始记录供审计/resume（resume 仍 `load_messages` 重载全部历史，与压缩同理）。无计划文本时 `handoff` 返回 false、不改动（安全回退）。
- **subagent**（`runner/subagent.rs::run_subagent`）：`task` 工具触发子 agent 运行；子 SessionState 用独立 agent（explore 只读 / build 全工具，默认 explore）。**plan 模式 subagent guard**（`runner/subagent.rs:59`，先于 `resolve_agent`）：plan agent 仅可派发 `explore`，其它类型（含 `build`）以 "Unknown subagent_type" 拒绝（不提 build 存在）；act 模式不受限。plan prompt（`base_prompt_plan`）额外 `.replace()` 剥离 BASE_PROMPT 中的 build 广告子句，测试 `plan_prompt_strips_build_subagent_advertisement` 保护此不变式，事件经共享 `Sink` 转发到父级——`SubagentStart{id,kind,prompt,child_session_id}` / `SubagentEnd{id,ok,summary}`，外加 `SubagentChild{id, ev: Box<SessionEvent>}` 包装器——子回调把**所有**子事件（TextDelta/ReasoningDelta/ToolStart/ToolEnd/Done/Error）包进 SubagentChild 转发，而非仅透传 ToolStart/ToolEnd，供 TUI 路由到子 block 的独立 ChatView。`child_session_id` 供 TUI 加载子记录。子 agent 复用父的 client/store/cancel。一轮内多个 `task` 调用与其它工具调用**并发**执行（同上 `FuturesUnordered`）。**libsql 追踪**：若有 store，创建子 session 行 + `subagent_tasks` 记录（parent/child/prompt/result/status），子事件持久化到 `session_events`（fire-and-forget `tokio::spawn`），完成后更新 result + status。**subagent 超时**（`execute_call_with_timeout`，`runner/execute.rs`）：两阶段 select——Phase 1 赛跑 `run_subagent` 与三类信号（`HardCancel`/`TurnCancel`/`Timeout`，`task_timeout()` 默认 1800s）；信号胜出后 future **不 drop**（用 `&mut sub` 借用而非 move），Phase 2 给予 `subagent_drain()`（默认 15s）宽限窗口让子 agent 跑清理路径。`HardCancel` 经 `child_token()` 级联；`TurnCancel` 显式 `fire_child_turn_cancel`；`Timeout` 显式 `fire_child_cancel`（`lib.rs`，按 call_id 取消单个子的 hard-cancel token）使子 agent 在 drain 内停止。drain 内完成 → `Ok(o)` 路径（Timeout 时再覆写 DB 状态为 `Cancelled` 并返回超时错误）；drain 超时 → `force_cancel_subagent` 强制 `Cancelled` + prune registry + emit `SubagentEnd`。
- `compaction::should_compact`（`src/compaction.rs`）：双信号——token 估算（首轮即可触发，无需模型回传 usage）+ 模型回传 `last_usage.input_tokens`（**非** `total_tokens`，避免输出重的 turn 误触输入预算）；预算 = `min(context_threshold, context_limit - reserved)`，故 `reserved` 真正缩减可用窗口（不再是死字段）。摘要用 `small_model`。**摘要提示词为结构化模板**（`prompt::compaction_system_prompt` + `prompt::compaction_user_prompt`）：系统提示固定 anchored-context-summarization 角色；用户提示要求严格按 Objective / Important Details / Work State(Completed/Active/Blocked) / Next Move / Relevant Files 顺序输出 Markdown。`compact()` 先在 head 中查找既有合成 summary 消息（`[Conversation summary so far]` 前缀），剥前缀后经 `<previous-summary>` 块传入，summarizer **增量更新**而非重写。`compact()` 经 `compaction_split()` 决定切分点：当 turn 数 > `tail_turns` 时取理想轮界切分；**turn 数 ≤ tail_turns 但已超阈值时不再静默放弃**——改为回退压缩最旧一轮（或单轮时保留最近一条消息、压缩其前内容），保证超预算的短轮次对话仍被压缩而非整段塞给模型。`None` 仅当真正无可压缩（空或单条消息），caller 不 emit 任何事件；`Some(summary)` 时 runner 发 `TranscriptReset(new_msgs)` + `Compaction(summary)` 两个事件——TUI 收到 `TranscriptReset` 时清空 `chat.blocks` 并用 `replay_into_chat` 重建（显示与模型视图一致）。 **图片保留契约**：`compact()` 先经 `collect_head_images(head)`（上限 `MAX_PRESERVED_IMAGES=4`，取最近）收集 head 中用户/工具图片 URL，再经 `strip_images()` 把所有图片块从送入 summarizer 的输入中剥离（避免图片被摘要吞掉/计费），最后把保留的 ≤4 张图片作为 `image_url` 块附加到合成 summary 消息（`has_image()` 为真）。`resume()`（handoff 与 compaction 两条分支）与 live `plan_handoff` 对重建的合成消息同样 re-derive head 图片并附加——跨进程恢复后图片不丢。
- `streamline::streamline`（`src/streamline.rs`）：纯函数确定性精简——在 `run_loop` 内 LLM 调用返回后、`record` 持久化前，对完成的 assistant 文本做保义归一（live `TextDelta` 已投递原文，故 UI 所见不受影响，仅持久化 + 后续上下文副本被精简，与 compaction 把旧消息替换为摘要同范式）。散文行去尾空白、连续空行收敛为单行、首尾空白行裁剪；**fenced 代码块（` ``` ` /`~~~`）逐字节透传**，代码格式/缩进/嵌空行不动。配置 `OutputStreamlineConfig`（默认开启，`collapse_inline_ws` 默认关）；每条规则在 clean 文本上为 no-op，故既有 transcript 零回归。
- **reasoning_effort 出站透传 + 交错思考**（`runner/llm_call.rs::run_one_llm_call` + `runner/mod.rs`）：主 LLM 调用把 `session.config.reasoning_effort`（`low|medium|high`）写进 `ChatRequest`，由 llm 的 `to_body` 发顶层字段（OpenAI 风格思考深度）；`compaction::summarize` / `resume::generate_title` 后台调用显式置 `None`。`run_one_llm_call` 返回 4-tuple `(text, reasoning, tool_calls, usage)`——reasoning 从 `LlmEvent::ReasoningDelta` 累积。**交错思考**（`interleaved_thinking` 默认 `Some(true)`）：`run_loop` 在工具调用 turn 且 reasoning 非空时，将 `ContentBlock::Reasoning { text }` 持久化到 assistant 消息（Text 之前），经 llm 的 `push_assistant` 序列化为 `reasoning_content` 在后续请求回传——DeepSeek-V4 强制要求此行为（否则 HTTP 400）。非工具 turn 不持久化（API 忽略，省 token）。运行时热重载：调用方（TUI `/config`/`/model` 经 `UiCmd::ReloadConfig`）在 turn 边界调 `SessionState::apply_config_reload(cfg, new_client)` 原地替换 `client/model/config`。每条出站 LLM 请求还携带 per-agent `cache_salt`，由 `cache_salt_for(session)` 派生为 `<agent_name>:<session_id>`——主 agent turn、子 agent turn（child session id，每个子 agent run 得独立 `sub-<ULID>` 命名空间）、title 生成、compaction 均注入；开关 `Config.cache_salt`（默认 `Some(true)` 即开，env `OPENCODER_CACHE_SALT` 覆盖），让 vLLM / prefix-cache 后端按 agent 区分 KV 缓存、会话内前缀逐轮增长。
- `resume::resume`（`src/resume.rs`，低层原语）：从 Store 重建 SessionState，model/agent 取自存储的 session meta（忠实原配置）。重建时两条 reconcile 路径：① 卡在 `Running` 的 subagent task（进程在 subagent 中途被打断）标记为 `Failed("(interrupted)")`；② 悬空的 `tool_use`（assistant 请求了工具但 tool_result 未落盘）合成 error `ToolResult`，避免 provider HTTP 400。这两条仅在裸 `resume` 直调时生效，是 `resume_and_replay` 之下的安全网。
- `resume::resume_and_replay`（`src/resume.rs`，高层入口；TUI/CLI/web 的 resume 都走它）：先遍历父 session 所有 `Running` subagent task（`list_subagent_tasks` 按 `seq` 升序），逐个 `resume(child)` + `run(child, "")`（**只此一层、不递归**——子 agent 无 `task` 工具，不可能派发孙任务），把子结果回填进父 transcript 的**单条** Tool message（mirrors `run_loop` 把一轮工具结果批进一条 tool_msg 的语义），并 `complete_subagent_task`。回填发生在裸 `resume` 之前，故 `resume` 跑到时无 `Running` task、task 的 `tool_use` 也已 answer，两条 reconcile 路径对该 turn 失活——既不重复标 Failed 也不合成 error。子续跑的 messages/events 落到子 session（与 `run_subagent` 同 pattern）。签名 `replay_cancel: Option<CancellationToken>`：逐个 `replay_child` 前检查 token，已 cancel 即 break（剩余 Running task 留待下次 resume）；该 token 透传给 `replay_child` 作 `parent_cancel`。`replay_child` **有总体超时 + 可中断**（修复恢复卡死）：`select!` 把 `run_with_registry` 与 `config.replay_timeout()`（默认 300s，独立于 `task_timeout` 1800s）及 `parent_cancel` 竞速；child 现自带 `CancellationToken`（`resume` 重建时为 None，此处补装——否则 run loop 中断检查永不触发），任一非 run 分支胜出则 cancel child + drop run future（硬中止进行中的 LLM/tool 调用），返回 `(部分文本, false)` → 调用方 `complete_subagent_task(ok=false)` 标 `Failed` 并回填 error `tool_result`；权威文本已由 `session.record()` 落库故可恢复。`flusher.await` 加 30s 超时防 DB 写慢永久阻塞。CLI 把 token 创建**提前到 resume 之前**并传 `Some(...)`（Ctrl-C 挂同一 token，恢复阶段可中断）；TUI/Web 也传 `Some(token)`，即便 token 不显式 fire 亦有 300s 超时兜底。`generate_title` 用 small_model 异步生成标题。测试：`tests/resume_replay_timeout.rs`。
- `resume::replay_cancelled_tasks`（`src/resume.rs`；由 `run_with_registry`（`runner/mod.rs`）在 drain turn 进入 `claim_steers` **之前**调用）：收集父 session 的 `Cancelled` subagent task（经 handoff 孤儿过滤——`handoff_seq.is_some()` 时要求 task 的 `tool_use` 仍存在于 `session.messages`；且先过滤掉 `tool_use` 已有匹配 `tool_result` 的 task——如超时 subagent 父侧已回填超时错误结果，重跑会追加重复 tool_result 触发 provider HTTP 400），分两支：① **无 pending steer**（`store.pending_inputs(id, Delivery::Steer)` 为空）→ 逐个 `replay_child` 跑完（把 `session.cancel.as_ref()` 作 `parent_cancel` 传入，受 `config.replay_timeout()` + 取消令牌双重守护），回填 `tool_result` + `complete_subagent_task`（硬中止/崩溃续跑语义，正确不应删）；② **有 pending steer** → 调 `abandon_cancelled_tasks`：**不重跑**子 agent，直接为每个 task 回填终态 error `tool_result`（"cancelled: the user redirected this turn (steer)."，保证 transcript 无悬空 id）并把 task 标 `Failed`，使 drain turn 立即落到 `claim_steers` 消费用户重定向。这是 **steer-click-hang 修复**（旧逻辑对 `Cancelled` task 一律 replay，导致子 agent 在用户已提交 steer 的 drain turn 被静默重跑、占用工具回合、steer 被无限挂起）；标 `Failed` 而非 `Cancelled` 使该 turn 永不被再次 replay。子 agent 无 `task` 工具 → `Cancelled` 列表恒空 → 对子进程零影响。测试：`tests/resume_replay.rs::{replay_cancelled_tasks_abandons_when_steer_pending, *_cancel_token_fired/not_fired}`。
- **plan→act handoff**（`src/plan_handoff.rs::handoff`）：plan→act 切换时把 transcript 压成单条合成 user 指令（最后一条非空 assistant 文本 = 最终计划 + 执行指令前缀）。与压缩同范式——纯内存 `session.messages` 重置 + caller 发 `TranscriptReset`；store append-only 不动。`final_plan_text` 取最新非空 assistant 消息；无则 `handoff` 返回 false 不改动。**边界落库**：`handoff()` 调 `SessionState::after_handoff(seq, plan)` 把移交边界（pre-handoff store message 数 + plan 显示文本）写入 `handoff_seq`/`handoff_plan`（由 TUI `SwitchAndStart` 经 `SessionPatch` 持久化）。`handoff_message(plan_display) -> Message`（合成 `Role::User`+`synthetic=true`）抽出复用。`resume()` 若 `meta.handoff_seq` 有值，则 trim `[0..handoff_seq]` 并 `insert(0, handoff_message(plan))` 重建焦点 transcript——用 `else if` 使**移交主导于压缩**（dominant transcript reset，二者互斥）。该主导性现为双层强制：写入层 handoff 持久化（`persist_clear` / autopilot）与 compaction 持久化对称——前者设 `clear_summary:true` 清 `summary/summary_seq/summary_images_json`、并设 `clear_skill:true` 清 `skill` 列（否则 resume 从 `meta.skill` 重建 `skill_prompt`/`active_skill_names` 重载已清 skill），后者设 `clear_handoff:true`；resume 层 `meta.handoff_seq.is_some()` 时防御性把残留 `summary_seq` 置 None，使 `prev_skip=summary_seq.or(handoff_seq)` 取 handoff_seq 而非残留的较小 summary_seq（修复 compaction→handoff→resume→compaction 的 OFFSET 污染）。
- **plan 模式 bash 写拦截（`bash_guard`）**（`src/bash_guard.rs` + `runner/execute.rs`）：plan agent 执行 `bash` 前以启发式 `classify(cmd)` 检测写操作（重定向、变更命令、包管理器、git 写），命中则返回 `WriteBlocked` 错误引导模型改用只读命令。**注意：bash_guard 是工作流护栏（防止 plan 模式下意外写盘），非安全沙箱——Act 模式下模型拥有完全权限。**
- **能力门控工具集 + capability filter**（`src/tools/web_read.rs` / `web_extract.rs` / `serp.rs` / `serp_engines.rs` / `research.rs` / `chrome_headless.rs` / `web_fetch.rs` / `web_search.rs` / `computer_use.rs` + `runner/execute.rs`）：`web_read`（always-on，纯网页阅读：markdown 协商 + `llms.txt` 爬取 + 可读正文抽取；SERP 逻辑已迁出）、`serp`（`serp.rs` + `serp_engines.rs`，7 引擎 SERP 解析——Bing/Baidu/Sogou/DDG/**Google**/**GitHub**(repo search)/**HuggingFace**(model search)；`parse_search_results`/`SearchResult` 现居此模块，按 URL host 分发到 `serp_engines.rs` 的 7 个 per-engine 解析器，纯函数默认构建即单测）、`web_extract`（always-on，10 个站点固定分析 profile 的结构化提炼（含 HuggingFace：og:title + model card 正文）+ 通用回退）、`research`（always-on，多引擎搜索→去重合并→chrome 渲染→站点提炼→`.research/` 报告落盘的单工具 deepresearch 管线，复用 `chrome_headless::dump_dom`）、`chrome_headless`（always-on，fetch/resolve/html/screenshot 四动作，`resolve` 解百度/搜狗跳转链接、`html` 供 `web_extract` 提炼；可选代理透传——`dump_dom`/`chrome_base_args` 接 optional proxy，非空时注入 `--proxy-server` + `--proxy-bypass-list`（`<local>;127.0.0.1;localhost;::1;0.0.0.0`）；四个 `do_*` 用 `effective_proxy(ctx.proxy)` 取值，空/空白视为无代理）、`web_fetch`/`web_search`（feature-gated `browser`，经 obscura，其 `!Send` V8/Rc future 包在 `spawn_blocking`+`LocalSet` 内以保 `Tool::execute` 仍 `Send`；`web_search` 调 `serp::parse_search_results`）、`computer_use`（always-on，驱动 core 的 `ComputerUseLoop`）。runner 在构建请求 schema 前以 `CapabilitiesConfig::tool_enabled(name)` 过滤——能力关时模型根本看不到该工具。这些可选工具收拢进 **`tools` umbrella 子 agent**（plan-visible，区别于 plan-hidden 的 `build`），由 act 经 `task` 调度。`ToolContext.proxy`（取自 `Config.network.proxy`）供工具执行时拿到代理配置。
- **可排队控制命令（`src/control_cmd.rs`）**：`/act`、`/plan`、`/act_clear_context` 的单一真源——`parse(prompt)->Option<ControlCmd>` 精确（空白容错）匹配，`apply(session, cmd, on_event)` 切换 agent 或清空 transcript + 持久化 + 发事件，**不调用 LLM**。三个集成点全在 `runner`：① idle 短路（idle prompt 是控制命令时应用即返回，不进 run_loop）② queue 拦截（idle 边界连续消费控制命令直到真实 prompt，各不消耗 turn）③ steer 拦截（turn 边界防御性应用，不记为 user text）。ClearContext 复用 `handoff_plan` 存哨兵 `<<OPENCODER_CLEAR_CONTEXT_MARKER>>`（ASCII 框架保证不与真实 plan 文本冲突），`resume.rs` 检测哨兵则重建 fresh-start marker，否则按 plan→act handoff——无 schema 变更。

## 主流程
CLI/HTTP 入口 → 建/恢复 SessionState（store 可选）→ `run(session, prompt, on_event)` → run_loop 循环到 Done / interrupt / doom-loop 守卫 → （CLI）异步 generate_title。

empty prompt = drain / continuation 模式：不 push 合成 user msg，直接进 run_loop（web drain 依赖 store 中已 admit 的 steer/queue 提供输入；TUI plan→act 手动切换经 `SwitchAndStart` 也走此路径——但**先经 `plan_handoff::handoff` 把 transcript 清为只含最终计划**，系统提示变 act，act 以干净 ctx 执行计划）。

## 两段式 delivery：steer / queue drain 契约

steer 与 queue 都是「先以 pending 落库（`admitted_seq` 列、`promoted_seq=NULL`），run_loop 在合适边界才 promote 进历史」的延迟提交机制，但消费规则截然相反。权威实现：`claim_steers` / `claim_one_queued`（`runner/steer.rs`），drain 在 `run_loop`（`runner/mod.rs`）。

- **steer =「一把全吸收」**：每个 turn 边界顶部（cancel 检查之后、LLM 调用之前）调 `claim_steers` → `promote_inputs(sid, max_seq, Steer)`，SQL `... WHERE delivery='steer' AND promoted_seq IS NULL AND admitted_seq <= max ORDER BY admitted_seq ASC` 一次把**全部 pending steer** 提升进历史，逐条 emit `SteerConsumed{seq, text}`（seq 为 `session_inputs` 主键，让前端按身份收缩 pending 镜像）。steered 控制命令（`/plan` 等）防御性 apply、**不记为 user text**。无每 run 配额——多少条都在同一个边界吃掉。
- **queue =「FIFO 逐条排空，空才 Done」**：仅在 **idle 边界**（本轮 `tool_calls.is_empty()`）才进 drain；`claim_one_queued` → `claim_next_queue`（SQL `... WHERE delivery='queue' AND promoted_seq IS NULL ORDER BY admitted_seq ASC LIMIT 1`，`BEGIN IMMEDIATE` 原子 SELECT+UPDATE）每次取一条。控制命令（`/act`、`/plan`、`/act_clear_context`）apply 后 `continue` 连排、**不消耗 LLM turn**；碰到**真实 prompt** 则 record 一条（`synthetic=true`）、break 出内层让 LLM 跑这一个 turn；该 turn 跑完回到 idle 边界继续 `claim_one_queued` 取下一条 FIFO——**直到队列空才发 Done**。steer 是 turn 顶部 `claim_steers` 一次性提升全部 pending 的清空路径。

| 维度 | steer | queue |
|---|---|---|
| 触发边界 | 每个 turn 边界顶部 | 仅 idle 边界 |
| 单次消费 | 全部 pending（`admitted_seq <= max`） | 恰好一条（`LIMIT 1`） |
| 每 run 配额 | 无限制 | 至多 1 条真实 prompt |
| 控制命令 | apply 不入历史（防御性） | apply 不耗 turn，可连排 |
| 打断进行中 turn | 能——`turn_cancel`（子 agent `>` submit-now）经 LLM 调用与工具批的 `select!`（`await_turn_cancel`）短路，下一边界 `claim_steers` 吸收 | 否——必须等 idle |

测试锚点：`steer_followup.rs`（`steer_promotes_at_turn_boundary`、`multiple_steers_at_one_boundary_promoted_once`——3 条 steer 同边界全部提交、`queue_promotes_exactly_one_real_prompt_per_run_then_stops`、`steer_consumed_carries_pk_seq_not_admitted_seq`、`durable_pending_input_survives_until_drain`）；`control_cmd.rs::queue_drains_control_cmds_between_real_prompts`（队列 `[/plan,prompt,/act]`：前导控制命令不耗 turn、真实 prompt 跑一 turn 后 run 停止、尾部 `/act` 保持 pending）。
