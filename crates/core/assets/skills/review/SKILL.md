# Review

## Overview

把“当前需求完成了多少、为什么这样判断、能否上线、还需要做什么才能完全解决”收敛成证据驱动的评审。

## 澄清协议（存在影响评审结论的疑问时）

`review` 只基于可核验证据下结论；当一个未定事项会改变完成度判断或上线结论（验收标准二选一、证据互相矛盾、关键约束缺失）时，不得默认假设后直接签收；无疑问则不做任何澄清动作。

- `review` 不调用 `question` 工具提问：交互式澄清只属于规划类 skill；需要用户裁决的事项写入「卡点与对齐事项」，由用户在评审输出后处置。
- 先查再定：能从仓库、`rules/`、既有测试、`AGENTS.md`、当次 diff 查到的事实一律先查再定，不把提问当侦察手段。
- 查不到 → 显式假设继续评审：把推断逐条列入 `assumptions:` 清单，选最小意外解释并标注「结论基于假设」；绝不静默编造验收证据或给降级签收结论。

评审不是复述命令流水账，也不是看到测试为绿就签收。必须从原始目标、实际改动、用户行为、边界与失败路径、依赖影响、发布条件和持续运行能力上判断交付是否真实闭环。

默认只读：检查、复跑验证并给出结论，不修改代码、不提交、不发布。用户明确要求边评审边修复时，先形成评审缺口，再按优先级继续落地，修复后重新取证评审。

## Workflow

### 1. 重建需求与完成标准

- 读取用户原始需求、需求变更、仓库约束、相关计划、当前 diff、验证结果和发布规则。
- 复述这轮真正要解决的问题、交付边界、非目标，以及完全解决后可观察的成功标准。
- 对照实际执行路径检查是否偏航；派生计划或状态摘要不能覆盖用户的原始目标。
- 先用仓库证据和安全的只读检查解除疑问。仍会实质改变结论的歧义、权限或外部条件，必须标为待对齐或 blocker，不得猜测。

### 2. 建立评审维度与完成度

- 只选择与本轮相关的维度，不机械套表。常用维度包括：功能实现、业务规则、数据流与状态、错误与边界、兼容性、测试质量、依赖影响、发布与运行条件、观测与回滚。
- 每次必须给出 `需求完成百分比`。验收项可计数时，用有当次证据的通过项计算；不可精确计数时，给保守百分比或区间，并说明权重、置信度和不确定性。
- 百分比使用整数或 5%/10% 粒度，避免伪精确。只有相关功能、边界、验证、发布条件和交付卡点都闭环时，才能评为 `100%`。
- 不把代码存在直接等同于需求完成。区分：`代码存在`、`候选可验证`、`已部署`、`行为已验收`、`持续可承载`，不得跨级推断。

### 3. 以当次证据审查当前状态

- 对每个相关维度标注 `已完成`、`部分完成`、`未开始` 或 `无法判断`。
- 每个状态绑定可核验的具体证据：文件路径与行号、函数或类型、API/路由、配置键、测试名、命令及输出结论、日志时间点、响应字段、数据流节点或外部系统状态。
- 每条证据说明它支撑哪个成功标准、证明了什么、还不能证明什么。泛泛写“看过代码”“跑了测试”“diff 显示已改”不是有效证据。
- 完成项必须同时写清 `怎么验证` 和 `证据是什么`；缺一则按证据不足处理，不能计入完全完成。
- 优先复跑与改动范围成比例的测试、lint、构建、真实行为或生产等价验证，明确哪些证据是当次新鲜证据。陈旧摘要只能作线索，不能直接签收。
- 检查测试是否覆盖可观察行为、正常路径与关键边界/失败路径，是否存在删测试、跳过测试、弱化断言或用 fallback 掩盖错误的伪绿。
- 当前负面实证必须使冲突的历史完成态或签收结论失效，直到新证据重新闭环。

### 4. 审查全局影响与发布责任

- 从变更的公开接口、共享状态、配置、数据形状和事件流向上游与下游各扩一层，确认调用方、消费者和相邻能力没有被遗漏。
- 审查异常流、空态、重试、幂等、并发、超时、权限、敏感信息、迁移、兼容和回滚边界。
- 对跨服务或异步链路核对 source of truth、producer、consumer、identity、状态机、错误语义、幂等键、重试/超时、副作用和失败归属。
- 区分代码通过、候选 artifact 一致、实际部署、真实行为验收和持续稳定。版本记录或部署成功不能替代运行时 artifact 与行为结果核对。
- 若有线上发布面，要求真实行为、实际操作或生产数据内容的实质校验，并明确样本、观察窗口、阈值、单项回滚红线和 `T0` 重置条件。无发布面时说明生产等价验收为何充分。

### 5. 梳理卡点与对齐事项

- 主动检查会阻止一次性交付的授权、审批、权限、凭证、账号、环境、数据准备、外部系统、发布窗口、人为确认、跨团队依赖和不可自动执行操作。
- 同时回放过程中已经解除的卡点及解除方式，避免后续重复踩中同类问题。
- 每个当前卡点写清：状态、阻塞原因、受阻事项、责任方或所需输入、具体对齐动作、完成后如何验证。
- 无法确认的外部状态标为 `证据不足` 或 `待对齐`；不得用降级 fallback 假装已满足。
- 如果没有发现卡点，也要说明检查过的类别，以及当前证据不能覆盖的外部状态。

### 6. 回放评估逻辑并给出闭环路径

- 按因果顺序解释原始目标、实际改动、数据流、错误面、验证证据、依赖影响和卡点如何共同形成当前完成度与风险判断。
- 明确区分确认事实、风险假设和外部 blocker。
- 按依赖顺序列出达到完全解决所需的后续事项，区分必须闭环、风险处理和可选优化。
- 每个必须项给出验收方式；not ready 的 TODO 必须与证据缺口或 blocker 一一对应，不能给泛化建议。

### 7. 裁决上线状态

- 只有原始目标已满足、相关维度有充分新鲜证据、影响面已审查、阻塞项闭环、发布与回滚条件成立时，才能给出 `go-live ready`。
- 任一关键目标未满足、关键证据缺失、负面实证未解决、范围外改动会混入发布，或存在未闭环 blocker 时，结论为 `not ready`。
- `N/A` 必须说明为何与本轮无关；无理由的 `N/A` 按未验证处理。
- 结论必须指出置信度、最关键证据、剩余风险和下一次重新评审的触发条件。

## Output Shape

不强制固定模板；优先用以下短段落清楚回答评审问题：

- `原始需求与完成标准`：用户真正要什么、当前边界和是否偏航。
- `需求完成百分比`：当前百分比或区间、计算口径、置信度，以及阻止 `100%` 的因素。
- `已完成事项与判断证据`：逐项列出验收方式、当次证据、支撑的标准和证据局限。
- `全局影响与回归风险`：影响模块、契约、数据、配置、调用方、发布和观测结论。
- `卡点与对齐事项`：已解除和当前 blocker，以及责任方、所需输入、解除与验收方式。
- `评估逻辑`：为什么得到当前完成度和风险结论。
- `还需做什么`：达到完全解决的依赖顺序、每项验收标准和重新评审条件。
- `上线结论`：`go-live ready` 或 `not ready`，附最关键依据与剩余风险。

## Notes

- 仓库级指令和仓库自定义 go-live 标准优先于本 Skill。
- 评审范围是当前需求或候选发布面的真实影响面，不是对整个仓库做无边界巡检。
- 保持具体、可追溯、不过度包装。缺少证据时直接报告缺口，不给降级签收结论。
- `review` 负责交付与上线判断；`say-and-replay` 负责任意检查点的进度对齐快照，两者可以复用证据，但结论职责不同。
