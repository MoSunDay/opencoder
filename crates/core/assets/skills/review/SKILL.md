# Review

## Overview

评审 = 回答五个问题 + 裁决上线结论。答好五问本身就是产出，没有固定输出模板。

**评审停在逻辑层**：不执行测试、不跑回归、不实跑命令验证——评审对象是变更逻辑本身，以及变更对受影响模块逻辑的潜在影响。

## 问一：原始需求目标

- 回溯用户的原始需求，逐字复述目标与验收标准，不引申、不缩减、不重定义。
- 需求有变化时如实标注变化点。

## 问二：做了哪些事情及完成度

- 盘点实际改动。
- 完成度 = `completed/total` + 百分比（向下取整）。

## 问三：卡点

- 诚实暴露卡点：遇到过什么、卡在哪里、阻塞了谁、需要什么（授权、审批、权限、凭证、外部依赖）。
- 无卡点也要显式说明「无」。

## 问四：逐项逻辑核查

对每一项改动做逻辑层 review，逐项回答两条：

- **逻辑本身**：推导是否成立、分支/边界/异常路径是否自洽、与既有约定是否一致。依据 = 当次 diff 与相关代码位置（文件:行），静态引用即可，不要求实跑。
- **变更潜在影响**：列出被该改动直接/间接触及的模块（调用方、被调用方、共享类型/接口、依赖的不变量），逐模块判断其逻辑是否仍然自洽；无法静态判定的影响列入 `assumptions:` 或问五 TODO。

## 问五：下一步 TODO

- 列出距离完全闭环还缺的事项，按优先级排序。
- 每项写明落地路径与所需条件。

## 上线结论

五问答完裁决：`go-live ready | not ready`。

| 情形 | 裁决 |
| --- | --- |
| 五问任一缺失或空泛（无逻辑依据支撑） | 直接 `not ready` |
| 五问齐备且逻辑核查与影响面评审无未闭环缺陷 | `ready`，并给出一句话理由 |

## 证据纪律

- **先查再定**：能从仓库、`rules/`、既有代码与注释、当次 diff 查到的事实先查再定，不把提问当侦察手段；查不到的推断列入 `assumptions:` 清单，标注「结论基于假设」。
- **不向用户提问**：需要用户裁决的事项写入问三卡点，由用户处置；绝不静默编造评审结论。
