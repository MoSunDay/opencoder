# Task Plan

## Overview

把“先看当前现状，再把问题彻底闭环到可上线”收敛成唯一规划入口。

## 澄清协议（存在影响计划的疑问时）

存在任何一个会改变 `task-plan` 计划走向的未定事项（验收标准二选一、目标互相矛盾、关键约束缺失、不可逆取舍）时，必须先与用户对齐，不得自行假设后直接出计划；无疑问则不强制提问。

- 先查再问：能从仓库、`rules/`、既有测试、`AGENTS.md` 查到的事实一律先查再定，不把提问当侦察手段。
- `question` 工具可用（交互式 TUI；sandbox 模式常驻可见，act 模式由本 skill 解锁）→ 调用 `question` 向用户澄清：每次一句一个最关键问题，可附 ≤4 个候选选项，可在同一轮多问；拿到答复再收敛计划。
- 不可用（headless `run` / web，工具即刻返回「无监听」应答不阻塞）→ 显式假设继续规划：把推断逐条列入最终输出的 `assumptions:` 清单，选最小意外解释并标注「计划基于假设」；绝不静默编造验收标准或替用户拍板不可逆取舍。

当需求极复杂、用户要求“尽可能列细”、或普通计划不足以降低执行理解成本时，`task-plan` 进入高颗粒度模式，输出可照着执行的操作清单，并单独做遗漏复查。

核心流程：

1. 重建问题定义、交付边界、非目标和上线目标
2. 回想整个事件流程，确认从触发、调查、决策、执行、验证到上线观察没有未解释的疑问或卡点；如有，必须提出并与用户对齐
3. 以上线标准审查当前现状，区分已确认问题、风险假设和外部 blocker
4. 识别根因、阻塞依赖、遗留 TODO 和隐性发布缺口
5. 生成按阶段、优先级和依赖顺序排序的闭环计划
6. 对复杂需求补充目标、位置、具体操作、预期结果、验证方式、失败处理和完成判定
7. 输出线上或生产等价验证方案，要求从用户行为、实际操作或生产数据内容上做实质校验
8. 做遗漏复查，把未覆盖项纳入计划、标成 blocker，或说明不属于本轮范围
9. 给出达到可上线状态前的关键路径与最终判断
10. 对跨服务合约和持续运行能力建立证据成熟度、保鲜 SLO、观测阈值和失效规则
11. 如果存在依靠当前上下文、仓库证据和安全检查仍无法解决的强卡点，必须通过向用户提问的方式对齐，不得猜测或绕过

当用户调用本 Skill 时，默认目标是“彻底规划和收敛闭环路径”。如果用户要求边规划边修复或直接继续实现，则先用本 Skill 收敛关键路径，再按优先级继续落地，不能停在规划。

## When To Use

- 用户明确提到“做个 task plan”“梳理一个彻底解决方案”“给上线闭环规划”“把剩余 TODO 全部拆出来”
- 用户要求“极度复杂”“尽可能列细”“减少理解成本”“好好想想是否遗漏”“完整详尽规划”
- 某个需求、修复、重构或候选发布面还没达到可上线状态，需要先明确剩余工作和推进顺序
- 你需要从全局视角判断“当前差在哪里”，并把它整理成可以持续推进到上线的执行计划

如果用户只要一次收尾总结、上线复核结论和 TODO、不需要闭环路线图，优先用 `verify-and-summary`。如果用户明确要求直接修复，不要停在规划，应在规划后继续推进代码和验证。

## Scope Rule

“全局视角”指的是当前问题或候选发布面的真实影响面，而不是对整个仓库做无边界巡检。

默认应纳入：

- 当前问题主链路、关键边界、异常流、空态和失败路径
- 直接依赖、被依赖模块，以及与之相邻的能力面
- 相关接口契约、配置项、环境变量、权限、数据流和发布假设
- 当前影响面内已有的 `TODO`、`FIXME`、`HACK`、临时兜底和已知历史缺陷
- 与上线闭环直接相关的测试、构建、脚本验证、UI 验收、观测和回滚准备
- 与上线判断直接相关的线上或生产等价验证方案，且必须能从真实行为、实际操作或生产数据内容上证明功能达成

默认不纳入：

- 与当前交付无关的长期债务
- 没有证据表明会影响本次上线判断的泛化优化
- 纯风格化重构或缺少产出价值的顺手改造

## Workflow

### 1. 建立规划上下文

- 先读取仓库级约束，例如 `AGENTS.md`、`agents.md`、相关 memory 文档、当前 diff、测试入口和发布约束。
- 明确这次要解决的“当前问题”是什么：功能未完、质量不稳、发布风险，还是历史债务混入。
- 重述成功标准、失败标准、非目标、未知点和用户决策点。
- 按时间线和因果链回想整个事件流程：需求触发、已有尝试、证据来源、关键判断、当前状态、剩余动作、验证与上线观察。
- 对每个流程节点检查是否还有疑问、缺证据、决策分歧、权限/数据/环境卡点或跨团队依赖；如有，先写成需要与用户对齐的 gating item，不能假装计划已经闭环。
- 先用当前上下文、仓库证据和安全的只读检查尝试解除卡点；如果仍是无法继续或会实质改变方案的强卡点，必须直接向用户提出具体问题完成对齐，并在对齐前将其保持为 blocker。
- 如果工作区存在真实改动，优先用 `git status --short`、`git diff --stat` 和相关模块文件收敛范围。
- 将“能力实现迁移”“默认流量切换”“旧链路退出”拆成三个独立决策。用户已经明确默认路由、共存边界或退出条件时，计划必须保持该决定；不得仅因出现“完全迁移”字样就自行推断切默认或删除 legacy。
- 当仓库或任务提供 Any Home 规划接口时，先读取 [references/any-home-plan-run.md](references/any-home-plan-run.md)，以目标 Action/Query 为起点，通过 `scripts/any_home_planning.py context` 查询与任务锚点相邻的实体和关系。该查询会写入 `QueryRecord`；计划不得只依赖对话中未经 readback 的记忆。
- Any Home 中已有知识优先于向用户重复提问。上下文仍缺失时，先检查已有 `SupportRequest`，再把不可解除的数据、能力或判断缺口明确写成新的求助。

### 2. 以上线标准审查当前现状

- 按 [references/launch-closure-plan-checklist.md](references/launch-closure-plan-checklist.md) 审查功能完整性、兼容性、遗留风险、验证闭环、发布准备和复杂任务遗漏面。
- 输出时明确区分：
  - `已确认问题`
  - `风险假设`
  - `外部依赖 / blocker`
- 前端场景必须纳入 UI 视角验收；涉及危险操作时优先确认根因和发布护栏，不用兜底掩盖问题。
- 按以下证据成熟度分别判断，不得跨级推断：
  1. `代码存在`：静态实现和单元测试可见。
  2. `候选可验证`：跨模块/跨仓测试、构建和迁移检查通过。
  3. `已部署`：线上运行 artifact、配置、schema 和仓库候选一致。
  4. `行为已验收`：真实或生产等价输入产生正确数据、状态和副作用。
  5. `持续可承载`：在明确样本与观察窗口内满足成功率、时延、保鲜、错误和回滚门禁。
- 任一当前负面实证都必须使冲突的历史 attestation、完成态或签收结论失效，直到新证据重新闭环。

### 2.1 建立合约与保鲜矩阵

- 跨服务、异步任务、数据保鲜或迁移任务必须列出：source of truth、producer、consumer、identity、请求字段、响应码/响应体、状态机、幂等键、重试/超时、顺序/并发、副作用、鉴权和失败归属。
- 同时核对仓库声明、部署 manifest、线上 effective config/schema/artifact、AP 账本和 local memory；任何不一致都按 drift 处理，不能任选一份作为成功证据。
- 版本 payload/readback 只证明版本记录一致，不证明运行时实际使用同一 artifact。若平台会用 workflow/deployment/global 的当前 effective image、model、agent version 或路由覆盖版本内声明，必须分别规划“版本记录 readback”和“真实 execution build detail/runtime artifact”核对；candidate 验收期间不得提前恢复会影响实际执行的 effective 配置，补偿必须绑定 candidate 接受/拒绝生命周期。
- 版本候选默认必须与自然流量做运行时隔离：显式 version 应使用 version-scoped artifact，不得通过修改 workflow/deployment/global effective 配置让未晋级 artifact 影响其他版本。若平台暂不支持版本隔离，计划必须把平台根因修复或独立 workflow/deployment 作为明确决策点，不能把 `default=false` 当成隔离证据。
- 任何会修改共享 effective 配置的工具，都必须在写入前持久化不可覆盖的 rollback journal。计划需覆盖“远端写成功、本地进程崩溃”“重试时目标已 matched”“补偿再次中断”，并要求显式 rollback/restore 入口和读回验证；进程内变量或最新一次 result 文件不能作为可靠锚点。
- 对 list/detail/callback/polling 等多个读写面，要求 canonical identity、终态和错误语义一致；禁止用某一个详情接口的正确结果掩盖列表或消费面的陈旧数据。
- 严格 consumer 合同上线前，先让 producer 产生新 canonical wire，并证明旧 consumer 可安全消费；禁止用 consumer 兼容旧歧义 wire 掩盖 producer 未迁移。发布计划必须写明 producer/consumer 顺序和每一步的跨版本兼容证据。
- 持续保鲜计划必须定义 freshness source、刷新触发、最大陈旧时间、last-success/last-error 可见性、stale 行为、巡检频率、指标/告警、观察窗口和责任方。
- “期间无报错”必须收敛为当前链路内零未处理异常、零合约错误、零静默降级；预期失败必须有明确响应、状态和可观测的有界重试。
- Webhook/callback 计划必须明确 auth-before-parse：在解析或记录业务 body、执行查询和写入副作用前完成签名/token/replay 验证；同时覆盖集中脱敏和无效请求零写入。
- 运行时必需 Secret 必须在启动或 readiness/release preflight 阶段验证键名与可用性，不能等到首个业务请求才暴露缺失；轮换要分别证明新凭证可用和旧凭证已失效。

### 3. 提炼根因与缺口地图

- 对每个核心问题先解释根因，不要把临时兜底当成闭环方案。
- 把缺口至少分成这几类：
  - `功能闭环`
  - `兼容性 / 回归`
  - `数据 / 配置 / 环境 / 权限`
  - `验证 / 测试`
  - `发布 / 观测 / 回滚`
  - `线上 / 生产等价验证方案`
  - `遗留债务是否需要纳入本次上线`
- 识别关键路径：哪些项不做一定不能上，哪些项可以并行，哪些项可以延后。

### 4. 产出闭环执行规划

- 规划必须按依赖顺序展开，而不是无序罗列。
- 每个计划项至少包含：
  - `优先级`：P0/P1/P2/P3
  - `阶段`：阻塞排除 / 开发闭环 / 回归验证 / 发布准备 / 上线观察
  - `动作`
  - `完成定义`
  - `验收方式`
  - `验证 / 上线验证影响`
  - `依赖 / blocker`
  - `当前状态`：可立即执行 / 依赖外部条件 / 需进一步确认
- 对复杂需求或用户要求“列细”时，每项还要补充：
  - `目的`
  - `要读 / 要改的位置`
  - `具体操作`
  - `预期结果`
  - `风险与失败处理`
  - `完成判定`
- 对需要一并处理的遗留问题，要显式说明“为何必须纳入本次闭环”，避免 TODO 漏项。
- 如果 Any Home 规划接口可用，最终文本计划必须同时转换成同构 `PlanRun`：每个 `PlanItem` 绑定依赖、Evidence 或 SupportRequest，调用 `scripts/any_home_planning.py create` 写回并读取详情。写回或 readback 失败时直接报告失败，不得把未持久化的结果表述为闭环。
- `PlanRun` 是不可变快照。重新生成时创建新记录并填写 `supersedes`，不得覆盖旧计划；读回返回 `fresh=false` 时，旧计划立即失去上线签收效力。

### 5. 输出线上或生产等价验证方案

- 每份计划都必须包含 `线上 / 生产等价验证方案` 或明确的 `不适用原因`。
- 有线上发布面时，写清上线后要验证的真实行为、操作路径或生产数据内容，明确数据来源、操作步骤、预期现象、判定标准和失败处理。
- 发布权限必须用对应环境、对应身份的脱敏写能力 preflight 证明；只读 detail/history 成功不能作为 create/update/deploy 权限证据。发布工具还要验证实际仓库拓扑、目标服务和 checkout 前置，不能只确认 CLI 命令存在。
- 没有线上发布面时，必须给出生产等价验证或本地验收方案，并说明为什么足以支撑可交付判断。
- 验证不能只写“看日志/看监控/确认部署成功”；日志、指标只能作为辅助证据，必须至少有一项来自行为结果、操作结果或数据内容的实质校验。
- 明确样本数量/类型、观察窗口、成功与失败阈值、数据/副作用唯一性检查、版本/配置漂移检查和触发回滚的单项红线；没有这些参数时不得把“稳定”写成完成定义。
- 明确观察窗口 `T0`：取最终发布/config/Secret/effective artifact 稳定与最后一个验收样本终态中的较晚时间；窗口内任何代码、schema、Secret、版本锁、路由或 effective artifact 变化都使既有持续稳定证据失效并重置 `T0`。
- 用户已确认样本数、观察窗口或阈值时直接采用，不得用 Skill 的通用建议擅自加码；用户未指定时才提出推荐默认，并明确记录为假设。

### 6. 做遗漏复查

- 在最终计划前单独做一轮遗漏检查，至少覆盖：
  - 边界条件、异常流、空态、重试、幂等、并发和超时
  - 已有能力、老调用方、老数据、老配置和相邻模块
  - 测试、构建、脚本、UI 或线上等价验证缺口
  - 新环境变量、表、字段、权限、迁移、删除数据或敏感信息风险
  - 临时兜底、隐藏错误、未根治问题、发布顺序、观测和回滚
- 遗漏项要么纳入计划，要么标记 blocker，要么说明为何不属于本轮范围，不能默默丢掉。
- 复查必须包含一次完整事件流程回看，确认计划没有跳过前因后果、当前状态、用户决策点或仍未解决的卡点；发现任何疑问都要列入对齐项或 blocker。

### 7. 收敛上线路径

- 给出从现在到可上线的关键路径，至少覆盖：
  - `上线前必须完成`
  - `可并行推进`
  - `上线窗口内执行`
  - `线上 / 生产等价验证方案`
  - `上线后观察 / 回滚条件`
- 如果存在用户决策点、跨团队依赖或环境前置条件，要明确写成 gating item，不能埋在正文里。
- 数据库发布必须从线上当前 revision/head 展开实际会执行的完整迁移链，量化最大表/索引体量、锁与耗时风险、剩余容量、前向恢复和服务回滚边界；dev 小数据通过不能外推 prod 迁移窗口。
- 对会留下部分 DDL、索引或回填状态的迁移，计划必须逐对象定义 postcondition 和重复执行语义；“表/列存在”不能代表迁移完成。验收需在关键阶段注入中断并证明重跑收敛到同一 schema/data head。

### 8. 给出执行结论

- 明确说明当前是：
  - `已具备规划闭环路径`
  - `仍缺关键信息，计划无法收敛`
  - `当前问题范围过大，需要先切分`
- 若用户要求继续推进实现，按计划中的关键路径从 P0 开始执行，并在执行中随新证据更新计划。

## Final Output

最终回复至少覆盖：

- `问题与范围`：本次纳入的真实影响面、非目标和上线目标
- `事件流程回想与对齐项`：按触发、调查、决策、执行、验证、上线观察回看完整流程；列出仍需用户确认的疑问、卡点和 gating item，若没有则明确说明
- `现状审查`：已确认问题、风险假设、外部依赖
- `影响面地图`：功能、模块、数据、配置、权限、验证、发布和观测影响
- `闭环计划`：按优先级和依赖顺序排列的执行项
- `逐步操作清单`：复杂需求时写清位置、操作、预期结果、失败处理和完成判定
- `线上 / 生产等价验证方案`：基于真实行为、实际操作或生产数据内容的实质校验步骤和判定标准；无线上发布面时说明不适用原因和替代验收
- `遗漏复查`：未覆盖项的处理结论
- `上线路径`：发布前、发布时、发布后的关键动作
- `最终判断`：是否已经形成可执行的上线闭环方案，以及仍缺什么

## Severity Guidance

- `P0`：确定阻塞上线，例如核心链路不可用、数据破坏、安全问题
- `P1`：高概率导致主功能错误、明显回归或关键模块能力退化
- `P2`：真实存在但不一定阻塞上线的缺口，需要结合发布窗口判断
- `P3`：低风险改进项或可后续处理的工程问题

## Notes

- repo 指令优先于本 Skill；如果仓库对测试、发布、UI 验收、数据库安全或文档维护要求更严格，按仓库规则执行。
- 该 Skill 的目标是“把当前问题闭环到可上线状态”，不是生成一份看起来很完整但无法执行的长清单。
- 高颗粒度拆解必须服务于执行，不为了显得完整而扩大到与本轮需求无关的历史债务。
- 如果审查过程中出现新的证据，应更新计划，而不是坚持已经失效的假设。
- 只要完整事件流程中仍存在未解释的疑问、缺证据、卡点或用户决策点，就不能把计划表述为已经完全收敛；必须把这些内容显式提出并等待对齐，或作为 blocker 纳入关键路径。
- Any Home 第一阶段仅承载查询、证据、求助、计划持久化和保鲜。Skill 不因计划中出现低风险动作就自行执行它；执行权限必须由单独的 Action/Delegation 能力明确提供。
