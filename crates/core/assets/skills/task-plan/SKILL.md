# Task Plan

> **只规划不执行**：交付一份从当前现状到可上线的闭环计划，不改代码、不启动实现，计划交付即停。用户要求「边规划边修复」时，也必须先产出完整计划（含关键路径与 P0 顺序），经确认后再按计划落地。

## 澄清协议（question 工具）

会改变计划走向的未定事项（验收标准二选一、目标互相矛盾、关键约束缺失、不可逆取舍）必须先与用户对齐，不得自行假设后直接出计划；无疑问则不强制提问。

- **先查再问**：仓库、`rules/`、既有测试、`AGENTS.md` 能回答的事实一律先查再定，不把提问当侦察手段。

### `question` 参数与用法（由本 skill 解锁）

| 参数 | 用法 |
| --- | --- |
| `question`（string，必填） | 只放一个问题，一句话说清；不把多个问题合并进一次调用 |
| `options`（string[]，可选） | ≤4 个短候选答案，互斥且覆盖主流取舍；开放性问题省略该参数 |

- 调用示例：`{"question": "验收以单测全绿为准，还是以线上冒烟通过为准？", "options": ["单测全绿", "线上冒烟通过"]}`
- 返回值：工具结果即用户所选答案或原文答复，拿到答复再继续。
- 同一轮可对多个独立决策点分别调用（一次一个最关键问题），全部拿到答复后再收敛计划。
- 答复被用户跳过时（工具返回「用户跳过，自行判断」）：显式假设继续规划——把推断逐条列入 `assumptions:` 清单，选最小意外解释并标注「计划基于假设」；绝不静默编造验收标准或替用户拍板不可逆取舍。

## 计划覆盖（最终输出五要素）

### 1. `树立目标`

- 问题定义、交付边界、成功/失败标准、非目标和上线目标。
- 仍需用户拍板的事项显式列为 gating item，不自行假设。

### 2. `关键 context`

- 仓库级约束：`AGENTS.md`、`rules/`、当前 diff、测试入口、发布要求。
- 按触发→调查→决策→执行→验证→上线观察回看事件流程。
- 现状审查区分 `已确认问题` / `风险假设` / `外部依赖 / blocker`。
- 范围 = 当前问题的真实影响面：主链路、直接依赖与相邻模块、相关合约/配置/数据、影响面内 `TODO|FIXME|HACK` 与临时兜底。
- 不做无边界巡检，不纳入无关历史债务。

### 3. `TODO List`

- 按依赖与优先级排序的核心动作清单，每项含 `优先级`、`动作`、`完成定义`、`依赖 / blocker`、`当前状态`。
- `优先级` 分级：

| 级别 | 判定 |
| --- | --- |
| P0 | 确定阻塞上线 |
| P1 | 主功能错误或回归 |
| P2 | 真实但看发布窗口 |
| P3 | 低风险改进 |

- 复杂需求或用户要求「列细」时再补：`位置`、`具体操作`、`预期结果`、`风险与失败处理`、`完成判定`。

### 4. `TODO 验证手段`

- 每个 TODO 必须可验证——基于真实行为、实际操作或数据内容的实质校验（步骤、预期现象、判定标准）。
- 上线项给 `线上 / 生产等价验证` 或写明不适用原因与替代验收，日志/指标只作辅助证据。
- 证据成熟度五级逐项标注、不得跨级推断：

  `代码存在` → `候选可验证` → `已部署` → `行为已验收` → `持续可承载`

  审查与验收细则见 [references/launch-closure-plan-checklist.md](references/launch-closure-plan-checklist.md)。

### 5. `核心动作`（关键路径）

从现在到可上线的执行顺序：

- 上线前必须完成
- 可并行推进
- 上线窗口内执行
- 上线后观察与回滚条件

## 遗漏复查

最终计划前做遗漏复查：未覆盖项纳入计划、标 blocker，或说明不属于本轮，不能默默丢掉。

## Notes

- 目标是可执行的闭环方案，不是看似完整的长清单；拆解服务执行，不为显得完整而扩大范围。
- 审查中出现新证据时更新计划，不坚持已失效的假设。
- 事件流程中仍有未解释疑问、缺证据或用户决策点时，计划不得表述为已收敛：显式提出等待对齐，或作为 blocker 纳入关键路径。
