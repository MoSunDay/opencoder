# Launch Closure Plan Checklist

## 1. 需求与现状审查

- 当前问题、目标能力、发布面、成功标准、失败标准和非目标是否已经说清
- 业务目标、用户价值、调用方或使用者是否明确
- 是否已经按触发、调查、决策、执行、验证和上线观察回想完整事件流程
- 完整事件流程中是否还有疑问、缺证据、卡点、用户决策点或跨团队依赖需要先对齐
- 主链路是否闭环，边界条件、异常态、空态和失败路径是否有定义
- 当前 diff、相邻模块、接口契约和配置入口是否都已纳入审查面
- 是否存在必须由用户确认的产品、权限、数据或发布时间决策
- 能力实现迁移、默认流量切换和旧链路退出是否分别定义；计划是否保留用户已确认的默认路由/共存边界，而不是把“完全迁移”误写成默认切换或 legacy 删除

## 2. 根因与缺口识别

- 当前问题的根因是什么，是否还停留在临时兜底或表面修补
- 当前影响面内搜索 `TODO|FIXME|HACK|XXX`，识别是否有旧问题会被一并带入上线
- 是否有旧需求、历史 TODO 或半成品逻辑混入本轮范围
- 区分已确认问题、风险假设和外部 blocker，不要混写

## 3. 代码与模块影响

- 主链路涉及哪些模块、入口、接口、任务、脚本或 UI 页面
- 上游输入、下游输出、错误码、返回结构、事件、日志是否变化
- 是否影响已有 public API、CLI 参数、配置格式、文件路径或任务调度
- 是否影响共享组件、公共工具函数或基础设施脚本
- 是否需要拆分过大的文件、函数或目录以保持模块边界清晰
- 是否已为跨服务边界列出 producer/consumer、canonical identity、请求字段、HTTP/业务响应码、状态机、幂等、重试/超时、顺序/并发、副作用和鉴权矩阵
- 严格 consumer 是否排在 canonical producer 之后发布，并有旧 consumer 消费新 wire 的过渡证据；是否避免为旧歧义 wire 增加长期兼容 fallback
- list/detail/callback/polling 等读写面是否返回相同 identity、状态和错误语义

## 4. 功能与兼容性闭环

- 还有哪些功能分支、边界条件或异常流没有完成
- 新改动是否改变已有接口、参数语义、输出格式、权限模型或操作方式
- 老调用方、老数据、老配置和灰度环境是否仍可工作
- 边界条件、空态、异常态、重试、幂等、并发和超时是否覆盖
- 前端改动是否已经从 UI 视角检查页面、交互、样式、响应式、空态和错误态表现

## 5. 数据、配置与安全

- 环境变量、配置项、权限、依赖服务、任务调度和外部资源是否齐备
- 是否新增或修改表、字段、索引、缓存、队列、对象存储或外部资源
- 是否新增 cookie、token、权限或网络访问需求
- 是否涉及迁移、回填、双写、读兼容、缓存刷新、重建索引或回滚兼容
- 是否从线上当前 revision/head 展开完整迁移链，并量化最大表/索引体量、锁时长、容量、前向恢复和服务回滚边界；是否避免用 dev 小数据耗时外推 prod
- 部分 DDL/索引/回填是否逐对象检查 postcondition；是否避免把表/列存在误判为完成；是否有关键阶段中断后重跑收敛证据
- 是否涉及删除数据、不可逆写入或生产数据修复
- 是否存在明文敏感信息、危险默认值、越权访问、审计缺口或不安全发布假设
- Webhook/callback 是否在解析、日志和副作用前完成鉴权与 replay 校验；无效请求是否零写入且日志集中脱敏
- 运行必需 Secret 是否在 startup/readiness/release preflight 验证；是否有新凭证成功和旧凭证失效证据

## 6. 验证与回归闭环

- 是否已有与影响面匹配的单元测试、集成测试、端到端测试、构建、lint、脚本验证或手工验收
- 缺失的验证项是否已转成明确 TODO，并说明为什么现在不能跑
- 是否需要补专门的回归、压测、演练、dry-run、UI 截图或响应式验收
- 后端或运维是否需要日志、指标、trace、dry-run 或只读数据验证
- 未执行的验证是否说明原因、风险和补偿计划
- 证据是否明确区分代码存在、候选可验证、已部署、行为已验收和持续可承载，且没有用低成熟度证据替代高成熟度签收
- 当前负面实证是否已经使冲突的历史 passed/attestation/完成态失效
- 版本 payload/readback 与真实 execution build detail/runtime artifact 是否分别核对；workflow/deployment/global effective 配置是否会覆盖版本声明
- 非默认 candidate 是否真正 version-scoped；是否避免通过共享 effective 配置污染默认/其他版本；平台不支持时是否已明确选择根因修复或独立隔离对象，而不是把 `default=false` 当成隔离证据
- 共享 effective 配置变更是否在写前持久化不可覆盖 rollback journal，并覆盖写后崩溃、matched 重试、补偿中断和显式 restore/readback

## 7. 线上或生产等价验证方案

- 是否已经设计线上或生产等价验证方案，且方案能通过真实行为、实际操作或生产数据内容证明能力达成
- 是否明确数据来源、操作路径、预期结果、判定标准和失败处理
- 有线上发布面时，是否至少有一项线上校验来自行为结果、操作结果或生产数据内容，而不是只依赖部署状态、日志或指标
- 对应环境的发布写权限是否经过脱敏 capability preflight；是否没有把只读 detail/history 成功误当成 create/update/deploy 权限
- 无线上发布面时，是否说明不适用原因，并给出生产等价验证或本地验收方案
- 日志、指标、监控和告警是否只作为辅助证据，而不是唯一闭环证据

## 8. 发布准备与上线后保护

- 发布前置检查、dry-run、灰度策略、回滚条件、监控指标、日志和告警是否明确
- 上线窗口内是否有需要按顺序执行的动作，是否存在跨团队依赖
- 是否有外部服务配额、环境差异、窗口期限制或权限前置
- 上线后观察期需要关注哪些日志、指标、业务数据、实际操作结果和告警，何时触发回滚
- 是否需要把上线前、上线中、线上验证和上线后的操作拆成不同清单
- 发布工具是否适配真实仓库拓扑和目标服务，是否不存在强制依赖已退役 checkout、错误分支或无关服务的隐藏前置
- 仓库 manifest、线上 effective config/schema/artifact、AP 账本和 local memory 是否一致；不一致项是否作为 drift 阻断
- 是否定义样本数量/类型、观察窗口、错误/时延/保鲜阈值、重复副作用阈值和单项回滚红线
- 这些稳定门槛是否优先采用用户已确认值；只有用户未指定时才使用显式标注的推荐假设
- 是否定义 `T0` 为最终发布/配置/effective artifact 稳定与最后样本终态中的较晚时间；窗口内代码、schema、Secret、版本锁、路由或 effective artifact 变化是否重置观察窗口
- candidate 验收期间影响实际执行的 effective image/model/agent/路由是否保持稳定；失败补偿和成功晋级是否都有显式生命周期与回滚证据

## 8.1 持续保鲜与稳定性

- freshness source、刷新触发、最大陈旧时间和终态收敛时间是否明确
- last-success、last-error、freshness-state 是否可由调用方或运营方看到
- 刷新失败是否进入 stale/alert，而不是被 best-effort catch 静默吞掉
- “无报错”是否限定为链路内零未处理异常、零合约错误和零静默降级；预期失败是否有确定状态与有界重试
- 稳定性结论是否同时有真实行为/数据证据和日志、指标、告警辅助证据

## 9. 遗漏复查与交付可读性

- 计划是否按依赖顺序，而不是按想到的顺序排列
- 每个动作是否说明目的、位置、具体操作、预期结果、验收方式、失败处理和完成判定
- 风险假设和已确认问题是否分开
- 遗漏项是否有处理结论：纳入计划、标记 blocker，或说明为何不属于本轮范围
- 是否再次回看完整事件流程，并确认没有跳过前因后果、当前状态、用户决策点或仍未解决的卡点
- 是否为了显得完整而混入与本轮需求无关的历史债务

## Plan Output Schema

每个计划项至少包含：

- `优先级`
- `阶段`
- `动作`
- `完成定义`
- `验收方式`
- `验证 / 上线验证影响`
- `依赖 / blocker`
- `当前状态`

复杂需求或用户要求“列细”时，每个计划项还要包含：

- `目的`
- `要读 / 要改的位置`
- `具体操作`
- `预期结果`
- `风险与失败处理`
- `完成判定`
