# Launch Closure Plan Checklist

## 1. 需求与现状审查

- 当前问题、目标能力、发布面、成功标准、失败标准和非目标是否已经说清
- 业务目标、用户价值、调用方或使用者是否明确
- 是否已经按触发、调查、决策、执行、验证和上线观察回想完整事件流程
- 完整事件流程中是否还有疑问、缺证据、卡点、用户决策点或跨团队依赖需要先对齐
- 主链路是否闭环，边界条件、异常态、空态和失败路径是否有定义
- 当前 diff、相邻模块、接口契约和配置入口是否都已纳入审查面
- 是否存在必须由用户确认的产品、权限、数据或发布时间决策
- 能力实现迁移、默认流量切换和旧链路退出是否分别定义；计划是否保留用户已确认的默认路由/共存边界，而不是把“完全迁移”误写成默认切换或 legacy 删除

## 2. 根因与缺口识别

- 当前问题的根因是什么，是否还停留在临时兜底或表面修补
- 当前影响面内搜索 `TODO|FIXME|HACK|XXX`，识别是否有旧问题会被一并带入上线
- 是否有旧需求、历史 TODO 或半成品逻辑混入本轮范围
- 区分已确认问题、风险假设和外部 blocker，不要混写

## 3. 代码与模块影响

- 主链路涉及哪些模块、入口、接口、任务、脚本或 UI 页面
- 上游输入、下游输出、错误码、返回结构、事件、日志是否变化
- 是否影响已有 public API、CLI 参数、配置格式、文件路径或任务调度
- 是否影响共享组件、公共工具函数或基础设施脚本
- 是否需要拆分过大的文件、函数或目录以保持模块边界清晰
- 是否已为跨服务边界列出 producer/consumer、canonical identity、请求字段、HTTP/业务响应码、状态机、幂等、重试/超时、顺序/并发、副作用和鉴权矩阵
- 严格 consumer 是否排在 canonical producer 之后发布，并有旧 consumer 消费新 wire 的过渡证据；是否避免为旧歧义 wire 增加长期兼容 fallback
- list/detail/callback/polling 等读写面是否返回相同 identity、状态和错误语义

## 4. 遗漏复查与交付可读性

- 计划是否按依赖顺序，而不是按想到的顺序排列
- 每个动作是否说明目的、位置、具体操作、预期结果、验收方式、失败处理和完成判定
- 风险假设和已确认问题是否分开
- 遗漏项是否有处理结论：纳入计划、标记 blocker，或说明为何不属于本轮范围
- 是否再次回看完整事件流程，并确认没有跳过前因后果、当前状态、用户决策点或仍未解决的卡点
- 是否为了显得完整而混入与本轮需求无关的历史债务

## Plan Output Schema

每个计划项至少包含：

- `优先级`
- `阶段`
- `动作`
- `完成定义`
- `验收方式`
- `验证 / 上线验证影响`
- `依赖 / blocker`
- `当前状态`

复杂需求或用户要求“列细”时，每个计划项还要包含：

- `目的`
- `要读 / 要改的位置`
- `具体操作`
- `预期结果`
- `风险与失败处理`
- `完成判定`
